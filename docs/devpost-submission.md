## Tagline

Recover a disrupted flight booking with typed WebMCP site tools — traveller and browser agent working on the same page, same session, same rules.

## What it does

An airline moves your flight. TripRescue lets you, or a browser agent acting with you, inspect the affected booking, state recovery constraints (arrive by, max extra cost, max stops), compare valid alternatives ranked by arrival time, preview the exact itinerary and price difference, approve the change in the page, and verify the updated booking. It runs against a real Duffel test-mode order: the airline change is generated by Duffel's sandbox, the change offers come from the booked airline, and the confirmation is a genuine sandbox order change verified by refetching the order.

## Why this use case is a strong fit for WebMCP

Trip recovery is a high-stakes, multi-step, stateful task where "guess the buttons from pixels" fails badly: the agent needs the *current* booking, must respect explicit limits, must never confirm without the traveller, and must prove the result. TripRescue exposes five small, single-purpose tools from the top-level page (`get_trip`, `find_recovery_options`, `preview_trip_change`, `apply_trip_change`, `get_change_status`) using the imperative `document.modelContext.registerTool` API. The tools operate on the page's own signed session: the agent never sees, sends, or guesses a booking id, a price, or our provider token. Read, search, preview, apply and verify are separate operations with honest `readOnlyHint` annotations and compact, normalized outputs.

## How it creates a better user experience

Every tool call updates the visible page before it resolves, so the traveller watches the same cards the agent is reasoning about, and an "Agent activity" log shows each call with its purpose and request id. The consequential write is protected by a server-issued preview, an order fingerprint, expiry and exact-price revalidation, single-use idempotent confirmation, and the site's own confirmation dialog, which the agent cannot bypass: `apply_trip_change` opens the dialog and returns `approval_required` if the traveller has not clicked Confirm. The ordinary website works identically without an agent; WebMCP is a progressive enhancement over the same actions.

## What people and agents can do together that was difficult or impossible before

The traveller states intent in one sentence ("direct, arriving by 1 PM, at most $150 extra"); the agent turns it into a typed search, reads the ranked options, stages the best one, and hands control back at the exact moment money and itinerary change. Neither party has to trust the other's arithmetic: constraints are enforced server-side, prices are revalidated at confirmation, and success is defined by the refetched booking, not by an HTTP 200. The result is a recovery flow that is faster than clicking through forms and safer than an autonomous agent, because the human decision is a first-class step in the tool protocol rather than a checkbox.

## Built with

Next.js 16 (App Router), TypeScript, Zod, Tailwind CSS v4, WebMCP imperative API (`webmcp-types`), Duffel Flights API (test mode, `@duffel/api`), Vitest, pm2 + nginx on Hetzner, GitHub Actions.

## Honesty notes for judges

Duffel test mode only. Synthetic schedules and prices (every sandbox change offer costs $125 with a $25 penalty). The airline change is simulated by Duffel on request. No live bookings, no real payments. The demo route (LHR → LTN on Duffel Airways) is the specific scenario Duffel's sandbox uses to generate airline-initiated changes.
