# TripRescue

**Recover a disrupted flight booking with typed WebMCP site tools — traveller and browser agent working on the same page, same session, same rules.**

Built for the [OpenAI WebMCP Challenge](https://webmcp.devpost.com/). TripRescue runs against a **real Duffel test-mode order** (or a clearly-badged local fixture), simulates an airline schedule change with Duffel's sandbox, and lets a traveller — or a ChatGPT / Chrome browser agent acting with them — inspect the disruption, search alternatives under explicit constraints, preview the exact change, confirm it in the page, and verify the changed booking.

> TripRescue is a hackathon prototype operating exclusively on Duffel test-mode orders. Its airline schedule change is generated by Duffel's sandbox and is not real operational flight data. Recovery options are order-change offers from the original booked airline. The project does not create live bookings or charge real payment methods.

## Why this is a WebMCP project

- The page registers **five small, single-purpose tools** with the imperative API (`document.modelContext.registerTool`) from the top-level document. No iframe, no declarative forms, no embedded chatbot.
- Tools operate on **the page's own signed session**. The agent never receives, sends, or guesses a booking id, a price, or a provider token.
- **Every tool call updates the visible page before it resolves.** The traveller watches the same cards the agent is reasoning about, and an "Agent activity" log shows each call.
- **Read → search → preview → apply → verify are separate operations** with explicit consequences and honest `readOnlyHint` annotations.
- The consequential write is guarded by a **server-issued preview**, an **order fingerprint**, **expiry**, **exact-price revalidation**, **single-use + idempotent confirmation**, and a **visible human confirmation dialog the agent cannot bypass**.
- The **ordinary website works identically without WebMCP** — the tools are a progressive enhancement over the same actions.

## The tools

| Tool | Input | What it does | Annotations |
|---|---|---|---|
| `get_trip` | `{}` | Current sandbox booking, simulated disruption, staged preview | `readOnlyHint: true` |
| `find_recovery_options` | `arriveBy?`, `maxExtraAmount?`, `maxStops?` | Creates a Duffel order-change request for the current slice; filters + ranks offers | `readOnlyHint: false` (creates a search resource) |
| `preview_trip_change` | `searchId`, `optionKey` | Revalidates the option, creates a *pending* Duffel order change, returns exact before/after + price | `readOnlyHint: false` |
| `apply_trip_change` | `previewId` | Opens the site's confirmation dialog; confirms with Duffel **only after the traveller clicks Confirm**; refetches and verifies | `readOnlyHint: false` |
| `get_change_status` | `{}` | Refetches the booking and reports whether the intended change is live | `readOnlyHint: true` |

All tools also set `untrustedContentHint: true` because their output includes provider-sourced data. Outputs are compact, normalized JSON (well under 1,500 characters) — never raw Duffel objects, never passenger data.

### How `apply_trip_change` keeps the human in control

Calling it opens the site's own confirmation dialog (sandbox badge, old vs new flights, penalty, fare difference, exact total, expiry). The tool waits up to 20 seconds for the traveller's decision:

- **Confirm** → the server revalidates ownership, fingerprint, expiry and price, confirms with Duffel (test balance payment if the total is positive), refetches the order, and returns `verified: true/false` based on the refetched itinerary.
- **Cancel / Escape** → `APPROVAL_CANCELLED`; nothing is booked.
- **No decision within 20 s** → `approval_required`; the dialog stays open, nothing is booked, and `get_change_status` reports the outcome later.
- **Aborted by the browser** → the dialog is closed and nothing is booked.

## Running it

```bash
npm install
cp .env.example .env.local     # fill in values (see below)
npm run dev                    # http://localhost:3000
```

| Variable | Notes |
|---|---|
| `TRIPRESCUE_PROVIDER` | `fixture` (default; deterministic local data, "Fixture Mode" badge) or `duffel` |
| `DUFFEL_ACCESS_TOKEN` | **Test-mode token only** (`duffel_test_…`). The server refuses any other prefix. Never exposed to the browser. |
| `SESSION_SECRET` | ≥ 32 random chars. Encrypts the HttpOnly session cookie. |

There is no runtime fallback between providers: a Duffel failure is shown as an error, never silently replaced with fixture data.

### Try the tools

- **ChatGPT desktop app** → open the built-in browser from the toolbar → visit the app → the address-bar arrow lists the site tools → ask ChatGPT, e.g. *"What happened to my trip? Find a direct replacement arriving by 6 PM for no more than £80 extra."*
- **Chrome** → enable `chrome://flags/#enable-webmcp-testing` → DevTools → Application → **WebMCP** to inspect and manually invoke each tool.

The demo route is **LHR → LTN on Duffel Airways (ZZ)** because that is the specific scenario Duffel's test mode uses to generate simulated airline-initiated changes.

## Architecture

```
Traveller / browser agent
        │
        ▼
Next.js page ──► top-level WebMCP registry (5 tools)
        │                    │
        └──── same client store ◄────┘   (every action updates visible state first)
                     │
                     ▼ same-origin JSON routes (Origin-checked, zod-validated)
              recovery service ── encrypted HttpOnly session cookie (opaque ids only)
                     │
        FlightRecoveryProvider interface
           ├── Duffel test-mode adapter (server-only; token never leaves lib/duffel)
           └── Fixture adapter (deterministic; tests + local demo)
```

- **Server-bound identity.** The visitor's Duffel order id lives only in an AES-GCM-encrypted cookie. Search results and previews are stored there as opaque `searchId` / `optionKey` / `previewId` records with the order fingerprint, constraints, price and expiry.
- **Provider as source of truth.** Every preview and apply refetches the order and the change offer / pending change. "Already confirmed" is derived from Duffel, so a replay after a lost response cannot mutate twice.
- **Stable error codes.** `NO_DEMO_ORDER`, `OFFER_EXPIRED`, `OPTION_NOT_IN_PREVIEW`, `TRIP_CHANGED`, `PREVIEW_EXPIRED`, `ALREADY_CONFIRMED`, `APPROVAL_CANCELLED`, `RATE_LIMITED`, `PROVIDER_UNAVAILABLE`, `ABORTED`, … each with `retrySafe`. Provider bodies, headers, and passenger fields never pass through.

Key files: `lib/recovery/service.ts` (the workflow + guards), `lib/webmcp/tools.ts` (tool definitions), `lib/client/store.ts` (shared page state), `lib/providers/duffel.ts` + `lib/duffel/normalize.ts` (adapter), `lib/session.ts` (cookie), `app/api/**` (routes).

## Limitations

- Duffel test mode only; synthetic schedules and prices; the "airline change" is simulated by Duffel on request.
- One adult, one-way, economy, original airline only (Duffel order changes search the booked carrier).
- No seats/bags/refunds/cancellation, no accounts, no webhooks (the confirm route refetches instead).
- The fixture provider's state is in-process memory (documented, non-durable). Deploy as one long-lived Node service (see `render.yaml`).

## Reset / recovery runbook

| Symptom | What to do |
|---|---|
| "No sandbox trip" | Click **Create sandbox trip** |
| Search returns nothing | Relax a limit explicitly, or **Start over** to seed a fresh future date |
| `OFFER_EXPIRED` / `PREVIEW_EXPIRED` | Run a new search and preview again |
| `TRIP_CHANGED` | Refresh; the booking moved under the preview — search again |
| Site tools not listed | Use the ChatGPT desktop built-in browser on a supported model, or Chrome with the WebMCP flag; the header chip shows registration status |
| Duffel unavailable | Set `TRIPRESCUE_PROVIDER=fixture` — the page badge will say **Fixture Mode** |
